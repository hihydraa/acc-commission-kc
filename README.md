# ระบบคำนวณค่าคอมมิชชั่นฝ่ายการตลาด

เว็บแอประบบคำนวณค่าคอมมิชชั่นรายเดือนของเจ้าหน้าที่การตลาด (เซลล์) จากไฟล์ PDF ที่ระบบขายส่งออกมา
(รายงานขายรายคันรถ + รายงานลูกหนี้ค้างชำระ + ไฟล์ master ระยะทาง/เซลล์) แล้วสร้างไฟล์ Excel ผลลัพธ์
ที่มีสูตรจริงทุกคอลัมน์ (ตรวจสอบ/แก้ไขต่อได้ใน Excel) — ตามกระบวนการที่สรุปไว้ใน skill
`marketing-commission-calc`

**ไม่มีฐานข้อมูล** — แต่ละคำขอ (request) ประมวลผลไฟล์ที่อัปโหลดมาในหน่วยความจำแล้วส่งไฟล์ Excel กลับทันที
ไม่มีการเก็บข้อมูลไฟล์หรือผลคำนวณไว้ที่ฝั่งเซิร์ฟเวอร์ เหมาะสำหรับรันบน Vercel (serverless)

ข้อยกเว้นเดียว: **หน้า `/settings`** เก็บ "ค่าที่แก้ไขได้โดยไม่ต้องแก้โค้ด" (รายชื่อลูกค้าที่ยกเว้น + เกณฑ์
ปริมาณ) ไว้ในไฟล์ JSON เดียวบน Vercel Blob (private) — เลือกใช้เพราะผู้ใช้ต้องการให้ทุกคนบนทุกเครื่องเห็น
ค่าเดียวกัน (ไม่ใช่แค่ localStorage ต่อเบราว์เซอร์) โดยไม่ต้องเพิ่มฐานข้อมูลเต็มรูปแบบ ดู
`src/lib/settings.ts` — ต้องมี env var `BLOB_READ_WRITE_TOKEN` (ตั้งอัตโนมัติเมื่อรัน
`vercel blob create-store <name> --access private --yes` แล้ว connect เข้าโปรเจกต์)

## รองรับหลายสาขา

กระบวนการคำนวณ (`src/lib/pipeline.ts`, `src/lib/calc/commissionEngine.ts`, `src/lib/excelExport.ts`)
เป็นกลาง ไม่ผูกกับสาขาใดสาขาหนึ่ง — ตัวเลขเฉพาะของแต่ละสาขา (ชนิดสินค้าที่นับ, เกณฑ์ปริมาณ, อัตรา/เกณฑ์
ค่าคอม, รายชื่อเซลล์, สัดส่วนแบ่งทีม, ข้อมูล master ที่ยืนยันไว้ล่วงหน้า) อยู่แยกเป็น config ต่อสาขาใน
`src/branches/*.ts`

ปัจจุบันตั้งค่าไว้ 2 สาขา (registry รวมอยู่ที่ `src/branches/index.ts`):

- **สามทอง/โลจิสติกส์** (`src/branches/samthong.ts`) — สร้างจากตัวอย่างอ้างอิง ST_8.69 (ส.ค. 2569)
  ที่อนุมัติแล้วตาม skill โมเดลเกณฑ์ปริมาณ/ค่าขนส่งแบบ "flat" (ตัวเลขเดียวทั้งสาขา ผูกกับไฟล์ต่อคันรถ)
- **กระนวน** (`src/branches/kranuan.ts`) — สร้างจากสเปค v2 ที่ยืนยันกับ PDF ต้นทางจริงแล้ว + ไฟล์อ้างอิง
  ที่อนุมัติของสาขานี้เอง ใช้โมเดล "departments" (เกณฑ์ปริมาณ/ค่าขนส่งแยกตาม "เลือกแผนก" A7/B7/68/B3 ที่
  พิมพ์อยู่ในหัวรายงานขายแต่ละไฟล์ ไม่ผูกกับชื่อไฟล์) — **ต่างจากสามทองในหลายจุดที่ยืนยันแยกต่างหากแล้ว**:
  ไม่มีเงื่อนไข "ต้องลงท้ายพันพอดี" เลย, แผนก B3 (กรอกหลังปั๊ม) ใช้ค่าขนส่ง/ลิตรคงที่ 0.10 แทนตารางระยะทาง,
  และระยะทางที่หาย/เกิน 209 กม. ต้อง **block** แถวนั้นไว้รอตรวจสอบแทนที่จะ default เป็น 0 แบบสามทอง (ดู
  `BranchConfig.freightMissingBehavior`) — การหักหนี้ค้างชำระใช้ `debtDeductionMode: "auto"` เหมือนสามทอง
  (หักเต็มจำนวนอัตโนมัติ) ตามที่ผู้ใช้ยืนยันชัดเจน แม้ไฟล์อ้างอิงที่อนุมัติของกระนวนเองจะเขียนไว้ว่าคอลัมน์นี้
  ตั้งต้น = 0 (ให้บัญชีพิจารณาหัก 50%/100% เอง) ก็ตาม — ผู้ใช้ตั้งใจ override ไฟล์อ้างอิงเดิม (ดูคอมเมนต์ใน
  `src/branches/kranuan.ts`)

### เพิ่มสาขาใหม่

1. สร้างไฟล์ใหม่ใน `src/branches/<ชื่อสาขา>.ts` implement `BranchConfig` (ดู `src/branches/types.ts`)
   — **ห้ามคัดลอกตัวเลขของสาขาอื่นไปใช้** ต้องขอตารางสัดส่วนแบ่งทีม รายชื่อเซลล์ และไฟล์ master ของสาขานั้น
   จากผู้ใช้ก่อนเสมอ (ตามหลักการของ skill) — ถ้าสาขาใหม่จัดประเภทรายการด้วย "เลือกแผนก" ในไฟล์รายงานขาย
   (แบบกระนวน) ให้ตั้ง `departments` แทน `minQtyLiters`/`requireExactMultiple`/`qtyMultipleOf` แบบ flat
2. เพิ่มเข้า `BRANCHES` array ใน `src/branches/index.ts`
3. หน้าเว็บ (`src/app/page.tsx`) จะแสดงสาขาใหม่ในตัวเลือกอัตโนมัติ

## หน้าตั้งค่า (`/settings`)

แก้ **รายชื่อลูกค้าที่ยกเว้น** และ **เกณฑ์ปริมาณ** (ต่อสาขา หรือต่อแผนกถ้าเป็นสาขาแบบ departments) ได้จาก
หน้าเว็บโดยตรง ไม่ต้องแก้โค้ด/build/deploy ใหม่ — มีผลกับการคำนวณครั้งถัดไปทันทีของทุกคนที่ใช้ลิงก์เดียวกัน
(`src/lib/settings.ts` merge ค่าที่บันทึกไว้ทับ default ใน `src/branches/*.ts` ตอนคำนวณแต่ละครั้ง — ค่า
default ในโค้ดยังใช้เป็นค่าเริ่มต้นก่อนมีใครแก้ และเป็น fallback ถ้าอ่าน Blob ไม่ได้)

ตัวเลข/กฎอื่นนอกเหนือจากนี้ (ผลิตภัณฑ์ที่นับ, อัตราค่าคอม, สัดส่วนแบ่งทีม, สูตร, ตารางค่าขนส่ง ฯลฯ) ยังคง
แก้เฉพาะในโค้ด `src/branches/*.ts` เท่านั้น — เพราะเป็นค่าที่เปลี่ยนไม่บ่อยและผิดพลาดได้ง่ายกว่าถ้าเปิดให้
แก้ผ่านหน้าเว็บโดยไม่มีการตรวจสอบ

## Deploy บน Vercel

```bash
npm install -g vercel   # ถ้ายังไม่มี
vercel
```

ไม่ต้องตั้งค่า environment variable หรือฐานข้อมูลใดๆ — โปรเจกต์นี้ stateless ล้วนๆ API route
(`src/app/api/calculate/route.ts`) ตั้ง `runtime = "nodejs"` ไว้แล้ว (จำเป็นสำหรับ `pdf-parse`/`exceljs`
ซึ่งใช้ Node API ที่ Edge runtime ไม่รองรับ)

ไฟล์ PDF ที่ใหญ่/หลายไฟล์รวมกันอาจใช้เวลาประมวลผลเกิน timeout เริ่มต้นของแผนฟรี (10 วินาที) — ปรับ
`maxDuration` ใน `route.ts` หรืออัปเกรดแผนตามความจำเป็น

`@napi-rs/canvas` (ใช้สำหรับ OCR แก้ชื่อลูกค้า — ดูหัวข้อถัดไป) มีไฟล์ native binary เฉพาะแพลตฟอร์ม —
ตรวจสอบว่า build บน Vercel (Linux) ผ่านและ OCR ทำงานได้จริงหลัง deploy ทุกครั้งที่อัปเดต dependency นี้

## โครงสร้างโค้ด

```
src/
  lib/
    parser/          PDF text -> structured data (รายงานขาย, รายงานลูกหนี้, master ระยะทาง/เซลล์)
    calc/             สูตรคำนวณ (freight table, commission engine, team split, rounding)
    excelExport.ts    สร้างไฟล์ .xlsx ด้วยสูตรจริง (VLOOKUP/IFS/IFERROR) ตรงกับ Template
    pipeline.ts       ประกอบทุกขั้นตอนเข้าด้วยกัน (parse -> calc -> debt match -> workbook)
  branches/           config เฉพาะสาขา (ตัวเลข/เกณฑ์/roster ต่างกันได้ต่อสาขา)
  app/
    page.tsx          หน้าอัปโหลด + แสดงผลสรุป
    api/calculate/    API route (multipart upload -> xlsx เป็น base64 ใน JSON response)
```

### ทำไมชื่อลูกค้าบางรายยังสะกดไม่สมบูรณ์ (OCR)

ไฟล์ PDF ต้นฉบับ (โดยเฉพาะไฟล์ master ระยะทาง/เซลล์) มีข้อบกพร่องที่ฟอนต์ฝังในไฟล์เอง — ข้อความที่
"มองเห็น" ถูกต้อง แต่ข้อความที่ "ฝังไว้ให้โปรแกรมอ่าน" ขาดวรรณยุกต์/สระบางตัว ยืนยันแล้วว่าเกิดกับทุก
library ที่ลองอ่าน (pdf-parse, pdfjs-dist, PyMuPDF) เหมือนกันหมด เพราะปัญหาอยู่ที่ไฟล์ไม่ใช่ตัวอ่าน

`src/lib/parser/ocrNames.ts` แก้ปัญหานี้เฉพาะ**ไฟล์ master** (เล็ก, หน้าเดียว) โดย render หน้า PDF เป็น
ภาพแล้ว OCR เฉพาะช่องชื่อลูกค้า (ใช้ตำแหน่งของรหัสลูกค้า ซึ่งอ่านถูกต้องอยู่แล้ว เป็นตัวช่วยหาตำแหน่ง) —
**ไม่ได้ทำกับไฟล์รายงานขาย** เพราะมีหลายร้อยแถวต่อไฟล์ OCR ทั้งไฟล์จะช้าเกินไปสำหรับ request/response
API และเสี่ยงกว่ามาก (ถ้า OCR อ่านตัวเลขปริมาณ/มูลค่าผิด จะกระทบการคำนวณค่าคอมโดยตรง ต่างจากชื่อที่เป็น
display-only) ผลคือชื่อลูกค้าในชีท Master ถูกต้องเกือบทั้งหมด แต่ชื่อในชีทรายคันรถ (มาจากไฟล์ขายโดยตรง)
อาจยังขาดวรรณยุกต์บางตัวอยู่ — **ไม่กระทบตัวเลขคำนวณเลย** เพราะระบบจับคู่ด้วยรหัสลูกค้า ไม่ใช่ชื่อ

**คำเตือนสำคัญเรื่อง dependency:** `@napi-rs/canvas` ต้อง pin ที่เวอร์ชัน `0.1.100` เป๊ะ (ดู comment ใน
`ocrNames.ts`) — เวอร์ชันใหม่กว่า (ทดสอบกับ 1.0.9) ทำให้ pdfjs-dist render ข้อความไม่ออกเลย ห้ามอัปเดต
dependency นี้โดยไม่ทดสอบ OCR ซ้ำ

### สิ่งที่ระบบ "ไม่" ทำอัตโนมัติ (ต้องทำเองนอกระบบ)

ตามประกาศ Incentive ข้อ 6-7: ลูกหนี้ค้างชำระเกิน Credit Term ที่ยังไม่จ่าย ให้ตัดค่าคอมเหลือ 50%
(เต็ม 100% ถ้าตกลงผ่อนตามตาราง) — เป็น manual adjustment ที่ฝ่ายบัญชีต้องปรับเองหลังได้ไฟล์จากระบบนี้
(ดูรายละเอียดใน `marketing-commission-calc/references/incentive-policy-mapping.md`)

### จุดที่ต้องตรวจสอบก่อนส่งมอบไฟล์ทุกครั้ง

ไฟล์ Excel ที่ได้มีสูตรจริงทุกคอลัมน์ ไม่ใช่ค่าที่คำนวณมาแปะ — **เปิดไฟล์ด้วย Excel/LibreOffice แล้วปล่อยให้
คำนวณสูตรใหม่ทั้งไฟล์ (คลิก Enable Editing / กด Ctrl+Alt+F9 ถ้าตัวเลขดูนิ่ง) แล้วเทียบยอดในชีท "ค่าคอมรวม"
กับผลรวม "รวมทั้งชีท" ของทุกชีทคันรถ** ก่อนส่งมอบ — ถ้าไม่ตรงกันคือบั๊ก ต้องตามหา ไม่ใช่ปัดเศษ
ระบบเองพยายามบังคับให้คำนวณใหม่ตอนเปิดไฟล์แล้ว (`fullCalcOnLoad`) แต่บาง viewer ก็ยังต้องกดคำนวณเอง

ดูชีท "หมายเหตุ" ในไฟล์ที่ได้ทุกครั้ง — มีคำเตือนเรื่องลูกค้าที่ไม่พบใน master, รายการที่มีข้อความ
"มิเตอร์ NN" ต้องยืนยัน, และรายการที่ตรวจสอบประเภท(R) ไม่ได้ ซึ่งทั้งหมดนี้ระบบไม่กล้าตัดสินใจเอง
